## Hard rules

> Non-negotiable for every task in this repo, regardless of the conventions
> captured below. Get explicit owner approval before deviating.
>
> **Scope of the rename rule:** it covers every identifier that already exists —
> variables, constants, functions, classes, methods, exports, route paths, DB
> columns, and config keys. A rename silently breaks callers, imports, persisted
> data, and public APIs this repo cannot see.
>
> **On tests:** state in one line what behaviour the test protects and why it
> needs to exist *before* writing it, then check the observed result against that
> stated expectation before calling it done. This applies to unit, integration,
> E2E, and automation tests alike.
>
> **On passwords:** a leaked secret is not un-leaked by deleting it — rotate any
> credential that was ever committed.
>
> **On the review pass:** it is a re-read of the work with fresh eyes — re-check
> the current session's tasks *and* what earlier sessions changed, looking for
> regressions, half-finished edits, and rules broken elsewhere. Report what you
> find; do not silently "fix" beyond the task's scope.

- **NEVER rename existing variables, constants, functions, or exports** without explicit owner approval. Add new ones alongside if needed — never change existing names. Renames break callers, imports, persisted data, and public APIs.
- **Name new functions and variables meaningfully** — intention-revealing (`resolveActiveSubscription`, not `handle2` or `tmp`). No cryptic abbreviations, no single letters outside loop indices, no numeric suffix to dodge a collision.
- **Tests assert real expectations, not liveness** — assert the actual outcome: returned values, persisted state, rendered output, or events. Asserting only `status === 200`, no-throw, or truthy is not a test; it passes while the feature is broken.
- **Passwords are hashed and at least 32 characters** — 32+ chars, stored only as a salted hash (bcrypt / argon2 / scrypt). Never store, log, echo, hard-code, commit, or return a plaintext password.
- **Never modify files outside the workspace root you were opened in.** No sibling checkout, parent directory, or other repository — those edits sit outside this repo's history and never reach code review. Need one? Stop and ask.
- **Mandatory review every turn** — after each completed turn, re-review this session's tasks AND earlier sessions' before moving on. Every fix and new implementation gets its own review pass. Costs extra tokens per turn; the owner opted in.

## Engineering rules

- **Language**: Use TypeScript in strict mode only — no `.js` / `.jsx` in application code.
- **Icons**: SVG only for icons and illustrations — no emojis in product UI.
- **DOM IDs**: Every DOM element must carry a module-specific prefixed ID (e.g. `{module}_{component}_{descriptor}`).
- **Re-renders**: No unnecessary component re-renders — memoise, split, subscribe narrowly on every component.
- **Modules**: Strict module separation — every feature has its own folder, routes, and tests.
- **Async**: No `setInterval`, no `setTimeout` for polling. Everything is event-driven: event bus, WebSocket push, AbortController, etc.
- **Logging**: All errors logged as structured JSON via `console.warn`/`console.error`/`console.info` with at least three fields: `level`, `component`, `event`. Never `console.error` alone; never swallow errors.
  - Never swallow an error: every catch block MUST either re-throw, return a typed error to the caller, OR emit a structured log entry. Bare `catch { /* ignore */ }` is forbidden.
- **No test-only backdoors**: The app MUST NOT contain any event, hook, seam, window handle, query-param gate, or route that exists only to make testing possible. Drive the actual UI a prospect drives.
- **Verification**: Always run a production build to verify changes. Never ship on dev-only checks.
- **CRITICAL — NEVER SAY "FIXED"/"DONE"/"COMPLETE" WITHOUT TRACING IT FIRST.**
  Saying a thing is done is a CLAIM. Verify the claim before making it, not after
  the owner questions it. Repeatedly announcing a fix and then discovering it was
  partial is the single most expensive failure mode in this repo — it burns the
  owner's trust and their time.

  Before the words "fixed", "done", "complete", "working", or "verified" are
  written, ALL of these must be true:

  | # | Must be true | How to check |
  |---|---|---|
  | 1 | The flag you set is actually READ by the thing you meant to stop | Grep every read. A boolean nothing consumes is a comment, not a brake. (`clientStickyPause` stops `resumeTour()` — it does NOT stop a tour already running; that needs `pauseTour()`.) |
  | 2 | The event you emit has a SUBSCRIBER | Grep for the listener. (`waiting_for_answer` has none — it is a marker, not a brake.) |
  | 3 | EVERY path to the bug is closed, not just the one you found | Server AND client, tool AND timer, LLM speech AND hub speech. |
  | 4 | It RAN, in a real session, and you saw the evidence | A green build is not a run. A skipped test is not a pass. Quote the log line or say "not yet executed". |
  | 5 | The state you rely on survives the lifecycle | One-shots that never reset; flags cleared on reconnect; timers re-armed. |

  If any is unmet, say what IS done and what is NOT, in the same breath — never
  "fixed" with the caveat buried later. Preferred wording: "implemented, not yet
  executed" / "holds X, does not yet hold Y".

  **No "partly".** A half-enforced rule is an unenforced rule: if the doc says the
  agent MUST do something, the code must CHECK it, not merely prompt for it. A
  rule the code does not check is a suggestion. Close it or state it as an open
  gap with a plan — never ship it as "partly done".

- **Post-implementation review (MANDATORY after EVERY fix or implementation)**: a
  change is not done when it compiles — it is done when it has been reviewed
  against the checklist below and the findings reported. Run this on your OWN
  work, before saying it is finished, and state the result explicitly.

  | # | Check | Fails when |
  |---|---|---|
  | 1 | **Right primitive?** | The call does something adjacent to what was needed — e.g. `dispatchAndRespond` for a call Deepgram never issued, or the lead-capture card (`ask_user_question`) used to ask a conversational question in a VOICE demo. Adjacent is not correct. |
  | 2 | **Right modality?** | A voice agent posts a form; a spoken flow requires typing; a visual change is announced but never shown. Match the channel the prospect is actually using. |
  | 3 | **Root cause, or one of several paths?** | The same bug is reachable from another route (server AND client, tool AND timer). Fixing one path and declaring victory is the most common failure here — grep for every caller before closing. |
  | 4 | **Idempotent / one-shot where it must be?** | A re-arming timer stacks cards, a reconnect re-fires a one-shot, a retry double-charges an LLM turn. |
  | 5 | **Wording factually true in EVERY state it can fire?** | A line reused across situations that claims something false in one of them ("That's the full walkthrough" mid-walkthrough). |
  | 6 | **Observable when it fails?** | Every branch — including the silent fallback — emits structured logging. No bare `catch {}`, no `.catch(() => {})`. |
  | 7 | **Rules honoured?** | No renamed existing names, no new events/vars when the vocabulary is closed. |
  | 8 | **Proven, or merely written?** | Say plainly which lines have actually EXECUTED in a run and which have only been typed. "Written but never executed" is not done. |
  | 9 | **Test measures the documented outcome?** | The assertion counts a proxy rather than the thing (toggle frames counted as turns; a client-only marker looked up in server logs). A green test proves nothing if it measures the wrong quantity. |
  | 10 | **Production build run?** | `npx next build` after the change, not just `tsc --noEmit`. |

  Report the outcome honestly, including checks that FAILED and were fixed as a
  result. A review that never finds anything is a review that was not done.

## 7. Don'ts / forbidden patterns

- **Always use meaningful names.** Every function, variable, constant, useState hook, and type — new OR existing — must describe what it does or holds. No single-letter names (except loop indices), no `temp`, `data`, `val`, `res`, `obj`, `item`, `thing`, `stuff`, `state`, `index`, `done`, `busy`, `current`, `entries`, `error` (without a subject prefix). The name must answer "of what?" / "by whom?" without reading surrounding code. Booleans must state the subject: `isAgentSpeaking` not `isSpeaking`, `allQuestionsAnswered` not `done`, `isSubmittingAnswer` not `busy`. If an existing name is vague or ambiguous, rename it in place (update all callers) — meaningful names are more important than name stability.
- **State-toggle patterns**: consolidate into dedicated methods (e.g. `setAgentSpeaking()` / `clearAgentSpeaking()` / `isAgentSpeaking()`) — no scattered inline assignments.
